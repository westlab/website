# 技術選定

## 要件

### 運用の前提

- サイトは学生が管理する（管理者が毎年変わる）
- 更新頻度は年数回程度

### 要求事項

- 更新の手順を単純にする
- 検索機能が使える
- ビルドが自動化できる
- デザインと内容を分離できる
- 全ページに日本語版と英語版を用意する
- セキュリティ確保のため、Webサーバ内でアップデートが必要なツールを最小限にする
- GitHubで管理する場合、サーバが侵害されても他のリポジトリを読み取られないようにする

## 決定事項

| 項目 | 決定 |
| --- | --- |
| サイト形式 | 静的サイト（WordPress を廃止） |
| 静的サイトジェネレータ | Astro |
| Webサーバ | Apache / Ubuntu（既存のものを継続使用） |
| HTTPS証明書 | Let's Encrypt / certbot（既存の運用を継続） |
| 検索 | Pagefind（サイト全体の全文検索） |
| ソース管理 | GitHub（public リポジトリ） |
| ビルド | GitHub Actions（`built` ブランチへ生成物を出力） |
| デプロイ | プル型（サーバの cron が取得 → rsync）。詳細は `deploy.md` |

---

## 各判断の理由

### なぜ WordPress をやめるのか

- 更新は年数回なのに、WordPress はセキュリティ対策のために頻繁なアップデートが必要になる
- 掲載内容に動的な処理は要らない

### なぜ静的サイトジェネレータを使うのか（手書きHTMLではなく）

手書きHTMLでは、ページの追加やデザインの変更に手間がかかる。ジェネレータなら、デザインと内容を分けて管理できる。

### なぜ Pagefind なのか

- ビルド時にインデックスを生成し、ブラウザ側で検索する。サーバに検索エンジンを立てる必要がない
- 生成後の HTML を走査して索引を作るため、ページを追加しても検索側の設定変更が不要
- 日本語（CJK）に対応している。Lunr.js などは日本語の単語分割が弱く、自前の実装が必要になる
- `lang` 属性ごとに索引が分かれるため、日本語ページでは日本語、英語ページでは英語の中を検索する

### なぜ日本語をルート、英語を `/en/` に置くのか

既存サイトが日本語をルートで運用しており、外部から張られたリンクを壊さないため。

全ページを対訳にするので、言語切り替えは常に1対1で対応する。未翻訳ページのフォールバック処理が要らず、実装は単純になる。

全訳運用の弱点は英語版の更新漏れに誰も気づかないことなので、人の注意力に頼らず仕組みで検出する。

1. 対訳の欠落を検出し、片方しかなければ警告する
2. ja/en 各ファイルの git コミット履歴を比べ、日本語版のほうが新しければ警告する。`scripts/check-translations.mjs` を `npm run check:i18n` と `git push` 時に実行する。フロントマターの手動フィールドは更新し忘れるので、実際の変更履歴で判定する
3. メンバー・業績などのデータは、1か所に両言語のフィールドを持たせる（`name_ja` / `name_en`）。1回の更新で両言語に反映され、二重管理にならない

### デプロイ方式

`deploy.md` を参照。サーバは HTTPS で認証なしに取得し、鍵を置かない。
